# Техническое задание: Интернет-магазин на Django/DRF

## 1. Введение и цель

Нужно создать полноценное приложение
интернет-магазина на Django. Для веб-интерфейса можно адаптировать предложенный
статический HTML/CSS-шаблон или написать собственную вёрстку. Выбор варианта не
влияет на оценку. Проект должен содержать:

- Веб-интерфейс (Django, шаблоны, сессии)
- REST API для внешних клиентов (DRF, JWT)
- (Бонус) GraphQL для аналитики как дополнительное улучшение
- Инфраструктуру: PostgreSQL, Docker
- Качество кода: читаемость, тесты и документация; типизация, линтеры и
  статическая проверка как бонус

Цель: показать понимание Django, DRF, работы с базой, архитектурных практик,
качества кода и готовности проекта к запуску через Docker Compose.

Предлагаемый HTML/CSS-шаблон:
https://github.com/MagicCodeGit/Hop-and-Barley.git

Точное визуальное повторение шаблона не требуется. Обязательно корректно
использовать Django Templates, наследование шаблонов и подключение статических
файлов. Отдельная оценка за сложность дизайна не выставляется; интерфейс должен
быть понятным и позволять выполнить все обязательные пользовательские сценарии.

## 2. Общие принципы

### 2.1. Статусы требований

- **Обязательное требование** — любое требование, которое явно не помечено как
  бонусное, рекомендательное или примерное. Обязательные требования образуют
  основную часть оценки в 100 баллов.
- **Темы** — проверяемые инструменты и знания из пройденного модуля. В обязательном
  функциональном блоке студент должен не только получить требуемый результат, но
  и продемонстрировать применение перечисленных тем. Замена конкретного инструмента
  допускается только там, где это прямо разрешено в ТЗ.
- **Бонус** — необязательное улучшение. Бонусные задания оцениваются отдельно в
  пределах бонусного пула и не требуются для получения 100 баллов за основную часть.
- **Рекомендация** — совет по реализации или оформлению, который не влияет на
  оценку сам по себе.
- **Примерное решение** — структура, модель или технический вариант, который можно
  изменить. При этом обязательное поведение и бизнес-правила должны сохраниться,
  а существенные отклонения необходимо объяснить в README.

### 2.2. Технические принципы

- **Веб-интерфейс** (пользователи через браузер) использует **session-based**
  аутентификацию (стандарт Django).
- **Внешние API** используют **JWT** для авторизации.
- GraphQL (если реализуется) доступен через **один эндпоинт** `/graphql/`.
- Структура проекта примерная — допускаются вариации, но должна быть логичная
  модульность.
- **Инфраструктура:** обязательное использование PostgreSQL, всё поднимается
  через Docker Compose.
- **Бонус:** использование альтернативного менеджера зависимостей (`poetry`,
  `pip-tools`, `uv`).

## 3. Функциональные блоки

### 3.1. Каталог товаров и поиск (`/` и `/products/`)

**Функциональность:**

- Список товаров с пагинацией
- Фильтрация по категории, диапазону цен
- Поиск по названию и описанию
- Сортировка по цене, популярности и новизне

Популярность товара рассчитывается как сумма проданных единиц
`OrderItem.quantity` в заказах со статусами `paid`, `shipped` и `delivered`.
Заказы в статусах `pending` и `cancelled` не учитываются. Эта же формула
используется для определения топ-продуктов, если реализована бонусная аналитика
в Django Admin.

**Темы:** CBV, шаблоны, ORM, оптимизация запросов

### 3.2. Страница товара (`/product/<slug>/`)

- Детальная информация (название, описание, цена, изображение, средний рейтинг)
- Список отзывов с рейтингами и форма добавления отзыва на основе `ModelForm`
- Кнопка "Добавить в корзину", выбор количества

**Правила отзывов и рейтинга:**

- Список отзывов доступен всем пользователям. Добавлять отзывы могут только
  аутентифицированные пользователи.
- Оставить отзыв можно только на товар, который пользователь приобрёл в заказе
  со статусом `delivered`.
- Пользователь может оставить не более одного отзыва на один товар.
- Рейтинг должен быть целым числом от 1 до 5. Ограничение проверяется формой и
  моделью, а при реализации бонусного REST API отзывов — также сериализатором.
- В обязательной части пользователь не редактирует и не удаляет опубликованный
  отзыв. Администратор может редактировать и удалять отзывы через Django Admin.
- Средний рейтинг не хранится в `Product`, а рассчитывается через `Avg` по отзывам.
  Если отзывов нет, веб-интерфейс показывает «Нет оценок», а API возвращает `null`.
- После успешной или отклонённой отправки отзыва веб-интерфейс показывает результат
  через Message Framework.

**Темы:** CBV, `ModelForm`, Message Framework, ORM, агрегации, валидация

### 3.3. Корзина (`/cart/`)

Корзина относится только к веб-интерфейсу и хранится в Django Session. REST API
не предоставляет отдельный ресурс корзины.

- Просмотр содержимого корзины
- Добавление, удаление, изменение количества
- Подсчёт итоговой стоимости, учёт остатка
- Хранение в сессии
- Проверка наличия товара

**Темы:** Django Sessions, Message Framework, бизнес-логика

### 3.4. Оформление заказа (`/checkout/`)

- Форма для данных доставки/контакта
- Выбор как минимум из двух условных способов оплаты без подключения внешней
  платёжной системы
- Создание заказа
- Очистка корзины после успешного оформления, страница подтверждения и сообщение
  о результате через Message Framework
- Обработка ошибок и валидация

**Темы:** Формы, Message Framework, транзакции

**Бонус: email-уведомления**

- После успешного создания заказа отправляются письма пользователю и администратору.
- В среде разработки используется консольный backend
  `django.core.mail.backends.console.EmailBackend`; настройка внешнего SMTP, Celery
  и фоновых задач не требуется.
- Отправка запускается после успешного завершения транзакции через
  `transaction.on_commit`.
- В тестах допускается заменить консольный backend на `locmem` и проверить письма
  через `django.core.mail.outbox`.

**Бизнес-правила заказа:**

- Оформить заказ может только аутентифицированный пользователь. После входа
  содержимое его сессионной корзины должно сохраниться.
- Новый заказ получает статус `pending`. Выбранный способ оплаты сохраняется в
  заказе, но не приводит к реальному списанию средств. В обязательной части статус
  `paid` устанавливает администратор.
- Допустимые переходы статусов: `pending → paid`, `pending → cancelled`,
  `paid → shipped`, `paid → cancelled`, `shipped → delivered`.
- Пользователь может отменить только свой заказ в статусе `pending`. Остальные
  переходы доступны только администратору. Статусы `delivered` и `cancelled`
  являются конечными.
- Заказы физически не удаляются. Отмена выполняется переводом в `cancelled`.
- Создание заказа, создание всех `OrderItem` и уменьшение остатков выполняются в
  одной транзакции. Если хотя бы одна позиция некорректна или товара недостаточно,
  заказ не создаётся и остатки не изменяются.
- При первом переводе заказа в `cancelled` остатки восстанавливаются. Повторная
  отмена отклоняется и не должна повторно увеличивать остатки.
- Цена каждой позиции копируется в `OrderItem.price` при оформлении и впоследствии
  не зависит от изменения цены товара.

### 3.5. Личный кабинет (`/account/`)

- Регистрация, вход/выход (session auth)
- Защищённая страница личного кабинета
- Список собственных заказов без дополнительной фильтрации
- Просмотр детальной информации только о собственном заказе
- Отмена собственного заказа в статусе `pending`
- Запрет доступа к заказам других пользователей

**Темы:** Аутентификация, ORM, формы, доступ

**Бонус: расширенный личный кабинет**

- Редактирование стандартных данных пользователя
- Смена пароля
- Фильтрация истории заказов
- Управление сохранёнными адресами доставки

### 3.6. Админ-панель (`/admin/`)

- Регистрация и управление категориями, товарами, заказами и отзывами
- Отображение `OrderItem` как inline внутри заказа
- Настройка `list_display`, `search_fields` и `list_filter` для основных моделей
- Изменение статуса заказа только по допустимым переходам
- Запрет физического удаления заказов
- Стандартный доступ только для пользователей с `is_staff`; отдельная система
  ролей и кастомных прав не требуется
- Управление пользователями через стандартный `UserAdmin`

**Темы:** регистрация и настройка моделей в Django Admin, поиск, фильтры, inline

**Бонус: расширенная админ-панель**

- Отдельная аналитическая страница: выручка, средний чек, топ-продукты и количество
  заказов по статусам.
- Кастомные массовые actions, которые соблюдают правила переходов статусов и
  корректно изменяют остатки.

### 3.7. REST API (`/api/`)

Ресурсы и действия (обязательный минимум):

| Ресурс       | Действие          | URL-шаблон                    | HTTP метод(ы)            | Описание                               | Авторизация    |
|--------------|-------------------|-------------------------------|--------------------------|----------------------------------------|----------------|
| Товары       | Список            | `/api/products/`              | GET                      | Пагинация, фильтрация, поиск           | Необязательно  |
| Товары       | Деталь            | `/api/products/<id>/`         | GET                      | Информация и средний рейтинг           | Необязательно  |
| Заказы       | Создание          | `/api/orders/`                | POST                     | Создание заказа из переданных позиций  | JWT            |
| Заказы       | Список своих      | `/api/orders/`                | GET                      | Список заказов текущего пользователя   | JWT            |
| Заказы       | Деталь            | `/api/orders/<id>/`           | GET                      | Детальная информация (только свой)     | JWT            |
| Заказы       | Отмена своего     | `/api/orders/<id>/cancel/`    | POST                     | Отмена заказа в статусе `pending`      | JWT            |
| JWT          | Получение токенов | `/api/token/`                 | POST                     | Получить access/refresh токены         | Нет            |
| JWT          | Обновление токена | `/api/token/refresh/`         | POST                     | Получить новый access-токен            | Refresh token  |

- REST API не содержит ресурса корзины. При создании заказа клиент передаёт
  непустой список позиций `items`, адрес доставки и способ оплаты. Каждая позиция
  содержит только идентификатор товара и количество.
- Пользователь определяется по JWT. Поля `user`, `price`, `total_price` и `status`
  не принимаются от клиента: цены берутся из базы данных, а итоговая стоимость и
  начальный статус рассчитываются сервером.
- Сервер проверяет активность товаров, положительное количество и достаточность
  остатков до создания заказа.
- Общие операции `PUT`, `PATCH` и `DELETE` для заказов недоступны. Отмена
  реализуется отдельным действием `cancel` во ViewSet.
- JWT реализуется через стандартные представления SimpleJWT: получение пары
  access/refresh и обновление access-токена.
- Права: пользователь видит/меняет только свои данные.

**Темы:** DRF, сериализация, ViewSets/routers, пагинация, permissions

**Бонус: расширение REST API**

- Регистрация пользователя через REST API.
- Публичное получение отзывов через `GET /api/products/<id>/reviews/`.
- Добавление отзыва после завершённой покупки через
  `POST /api/products/<id>/reviews/` с JWT.

### 3.8. Документация API

- Swagger/OpenAPI для REST API (например, `/api/docs/`)
- Примеры запросов, схемы, авторизация

**Темы:** Автоматическая документация (drf-spectacular, drf-yasg и т.п.)

### 3.9. (Бонус) GraphQL

- Один эндпоинт `/graphql/`
- Аналитические запросы:
    - Заказы: выручка, количество, средний чек, тренды
    - Продукты: популярные, остатки
    - Пользователи: активность, повторные покупки

**Темы:** Graphene/Django, резолверы, авторизация в GraphQL

> Примечание: GraphQL — бонус. Можно заменить на другие улучшения (например,
> расширенные тесты, CI/CD и т.п.).

## 4. Структура данных (База данных)

### Category

- `id` (PK)
- `name` (CharField)
- `slug` (SlugField, unique)
- `created_at`, `updated_at`

### Product

- `id` (PK)
- `name` (CharField)
- `slug` (SlugField, unique)
- `description` (TextField)
- `price` (DecimalField, значение не меньше 0)
- `category` (ForeignKey to Category, `on_delete=PROTECT`)
- `image` (ImageField / мультимедиа)
- `is_active` (BooleanField)
- `stock` (IntegerField, значение не меньше 0)
- `created_at`, `updated_at`
- `CheckConstraint` для неотрицательных `price` и `stock`

### Order

- `id` (PK)
- `user` (ForeignKey to User, `on_delete=PROTECT`)
- `status` (CharField: pending, paid, shipped, delivered, cancelled)
- `payment_method` (CharField)
- `total_price` (DecimalField, значение не меньше 0)
- `shipping_address` (TextField / отдельная модель)
- `created_at`, `updated_at`
- `CheckConstraint` для неотрицательной итоговой стоимости

### OrderItem

- `id` (PK)
- `order` (ForeignKey to Order, `on_delete=CASCADE`)
- `product` (ForeignKey to Product, `on_delete=PROTECT`)
- `quantity` (IntegerField, значение больше 0)
- `price` (DecimalField, значение не меньше 0) — snapshot
- ограничение уникальности пары `order` + `product`
- `CheckConstraint` для положительного `quantity` и неотрицательного `price`

Товар, который уже встречается в заказах, нельзя физически удалить — для снятия
его с продажи используется `Product.is_active`. Пользователь, у которого есть
заказы, также не удаляется каскадно вместе с историей заказов.

### Review

- `id` (PK)
- `product` (ForeignKey to Product)
- `user` (ForeignKey to User)
- `rating` (IntegerField с ограничением 1–5)
- `comment` (TextField)
- `created_at`
- ограничение уникальности пары `user` + `product`
- `CheckConstraint` для диапазона рейтинга от 1 до 5

*Примерное расширение:* модели Address, Payment и другие модели по необходимости.
Сами по себе дополнительные модели не влияют на основную оценку.

## 6. Качество кода и инфраструктура

1. **Обязательное качество кода**
    - Понятные имена классов, функций и переменных.
    - Разделение приложений и модулей по ответственности.
    - Отсутствие неиспользуемого и закомментированного кода.
    - Бизнес-логика не размещается в шаблонах.
    - Общие правила создания и отмены заказа переиспользуются веб-интерфейсом и
      REST API, а не дублируются во views и serializers.

2. **Рекомендация: докстринги**
    - Докстринги добавляются там, где назначение или бизнес-правила невозможно
      понять из имени и структуры кода.
    - Формальный процент покрытия кода докстрингами не проверяется.

3. **Бонус: типизация, линтеры и статическая проверка**
    - Осмысленные аннотации типов в собственном коде проекта.
    - `flake8` или аналог.
    - `mypy` с настройкой, необходимой для проверки Django-проекта.

4. **Тестирование**
    - `pytest-django`.
    - Основные сценарии: каталог, корзина, заказ, регистрация/вход, REST API,
      бизнес-правила.
    - Проверка ограничений (например, нельзя заказать больше, чем в наличии).
    - Проверка отзывов: запрет без завершённой покупки, запрет повторного отзыва,
      валидация рейтинга и расчёт среднего значения.

5. **Инфраструктура**
    - PostgreSQL.
    - Docker Compose для запуска приложения и базы данных.
    - Основные сервисы запускаются документированной командой
      `docker compose up --build`.
    - Миграции созданы и находятся в репозитории; команда их применения указана
      в README.
    - Настройки и секреты читаются из переменных окружения. В репозитории есть
      `.env.example` без реальных паролей и секретных ключей, а рабочий `.env`
      не добавляется в Git.
    - Все зависимости задокументированы (`requirements.txt`
      или `pyproject.toml`).
    - (Бонус) использование `poetry`, `pip-tools` или `uv`.

6. **Git workflow**
    - Осмысленные мелкие коммиты.
    - **Рекомендация:** использовать отдельные ветки там, где это помогает работе
      над проектом. Обязательной схемы и правил именования веток нет.

7. **Документация**
    - README: описание, установка, запуск, JWT, API-примеры, тесты и структура.
      README также описывает подготовку `.env`, применение миграций и запуск
      проекта командой `docker compose up --build`.
      Если реализованы бонусные проверки, README также содержит команды запуска
      линтеров и статического анализа.

100. Выполнение бонусных заданий не требуется для получения 100 баллов за
обязательную часть.

**Итого за обязательную часть:** 100

**Бонусные улучшения:** до 15 баллов.

Вы можете выполнить любое одно или несколько бонусных улучшений из списка.
Точное количество бонусных баллов определяет преподаватель с учётом сложности,
полноты, корректности и качества реализации. Фиксированная стоимость отдельных
бонусных улучшений заранее не устанавливается.

**Варианты бонусных улучшений:**

- GraphQL аналитика
- Расширенное покрытие тестами (>=80%)
- Email-уведомления с консольным backend
- Расширенная аналитика и массовые actions в Django Admin
- Расширенный личный кабинет: профиль, смена пароля, фильтры и сохранённые адреса
- Регистрация и работа с отзывами через REST API
- Типизация, линтеры и статическая проверка (`flake8` или аналог, `mypy`)
- CI/CD (проверка тестов и линтеров, сборка, деплои)
- Использование `poetry` или другого менеджера
